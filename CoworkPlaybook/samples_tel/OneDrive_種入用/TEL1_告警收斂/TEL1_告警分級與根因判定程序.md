# 告警分級與根因判定程序（摘錄）

> 文件管理：網路技術處　|　ZVT-NOC-P-0112　|　版次 2.4

## 1. 為什麼不能用告警數量判斷

電信網路是**樹狀拓樸**：匯聚節點（母站）底下掛著數十個小區。
母站一旦失聯，**底下每一個小區都會各自發出告警**，而母站本身通常只發一筆。

因此「告警數量最多的網元」代表的是**受災最廣的範圍**，不是**肇因**。
依數量排序處理，會先去處理一堆症狀，而真正要派工的那一台排在最後面。

## 2. 根因判定準則

```
步驟 1  把告警依網元彙總，標出每個網元的上層網元（查拓樸表）
步驟 2  對每一個母站，檢查它的下游節點是否**全數**告警
        全數告警 → 該母站是根因候選
        部分告警 → 該母站不是根因（問題在個別小區）
步驟 3  根因候選若有多個，取拓樸層級最高者
```

⚠️ **「全數」是關鍵字。** 下游有 23 個小區而 22 個告警，那是 22 個獨立事件；
23 個全部告警，才是母站把它們一起拖下水。

## 3. 處置與派工

| 判定 | 處置 |
|---|---|
| 母站根因 | 派工至母站，**不對下游小區逐一派工** |
| 個別小區故障 | 對該小區派工 |
| 傳輸品質劣化（minor） | 列入觀察，不立即派工 |

## 4. 常見誤判

1. **依告警數量排序**。見第 1 節。
2. **只看 critical 層級**。母站的確會發 critical，但下游小區發的是 major，
   數量多到會把 critical 淹沒在清單裡。
3. **把同一母站下的小區當成獨立事件各開一張工單**。
   正確做法是開一張母站工單，下游小區掛在底下。

## 5. 不得為之

- 不得在未查拓樸表的情況下判定根因。
- 不得對已判定為「母站根因」的下游小區重複派工。
- 不得將 minor 層級的告警自動結案而不記錄。

# 技能品質自評對照表（對照 Cowork 官方 4×25 評分）

> 官方在建立、更新或驗證技能時會**自動評測**並回傳 Skill Report，
> 滿分 100，四個面向各佔 25 分。分數帶：
> Excellent ≥ 85｜Good 70–84｜Needs work 50–69｜Poor < 50
>
> 這張表的用途，是讓學員在送出技能**之前**先自己檢查一遍，
> 而不是等 Skill Report 退件才回頭改。

## 四個面向與本技能的對應寫法

| 面向 | 官方要求 | 本技能怎麼滿足 |
|---|---|---|
| **Trigger clarity**<br>觸發清晰度 | 技能要在對的時機被啟動 | `description` 直接列出觸發詞：停線、產線停機、設備停機、line stop、machine down，並涵蓋「轉貼一封停線通報信」這種情境 |
| **Instruction specificity**<br>指示具體度 | 技能知道該做什麼 | 判定步驟拆成 4 步且**寫死門檻值**（4 小時／1–4 小時／< 1 小時、7 天內第 3 次、2 小時未排除），不是「請適當判斷」 |
| **Scope boundaries**<br>範圍邊界 | 技能不越界 | 獨立一段「何時**不要**使用」，明列三類該交給別的流程的請求，並要求明確說明不適用而非硬套 |
| **Robustness**<br>穩健度 | 面對非預期輸入仍安全 | 「遇到資訊不足時」規定缺 ETA 寫「待確認」不自行推估、無法判定就回問；「安全限制」禁止代為承諾與禁止降級安全事件 |

## 常見四種扣分寫法（官方明列）

| 問題 | 後果 |
|---|---|
| description 超過字數上限 | 技能**永遠不會載入** |
| description 沒有觸發詞 | 技能**永遠不會啟動** |
| description 範圍太廣 | 技能在**不該啟動時亂啟動** |
| 兩個技能搶同一批請求 | 兩個都可能啟動，須加上明確 handoff |

## 動手前自我檢查

- [ ] YAML frontmatter 有 `name` 與 `description` 兩個欄位
- [ ] description 裡看得到具體觸發詞，而不只是功能描述
- [ ] 有「不要使用」的反向邊界段落
- [ ] 判定門檻是具體數字，不是「視情況」
- [ ] 有寫資訊不足時該怎麼辦
- [ ] 有寫對外動作必須先核准

> 對照練習：把手冊裡任何一個舊版技能範例貼進 Cowork 建立技能，
> 看它回傳的 Skill Report 落在哪一帶，再對照本表逐項補齊，重跑一次比較分數變化。
